# ML-часть тренажёра ЭЛОУ-АВТ

Тренажёр отвечает на вопрос «что было в прохождении». Эта часть отвечает на два других:

1. **Что тренировать дальше конкретному оператору.** По ходу прохождения находится слабое место и
   собирается профильный сценарий на следующий раз.
2. **Чего не хватает самому тренажёру.** По результатам всех операторов ищутся системные провалы и
   предлагаются новые сценарии.

Главное правило: **ML ничего не внедряет сам**. Любой вывод — черновик в очереди, который утверждает
эксперт-человек. Оператору, проходящему тренировку, отсюда не уходит ничего: подсказка обесценила бы
проверку навыка.

## Быстрый старт

```bash
cd ml
uv sync
uv run pytest                                  # 36 тестов на корпусе из 36 прохождений
uv run python -m ml.cli analyze --source corpus
```

Разбор одного прохождения и рекомендация:

```bash
uv run python -m ml.cli advice --session EAVT-L2-NO-VERIFICATION-021 --source corpus
```

Системные проблемы по всем операторам:

```bash
uv run python -m ml.cli mine --source corpus --save
uv run python -m ml.cli proposals --status draft
uv run python -m ml.cli review <id> --approve --expert expert-1
```

Сервис:

```bash
uv run uvicorn ml.service:app --port 8100      # Swagger: http://127.0.0.1:8100/docs
```

## Локальная LLM

Модель формулирует текст для эксперта. Числа, уровни, первопричины и параметры сценария она **не
выбирает** — их считает Python, иначе рекомендация перестала бы быть воспроизводимой. Без запущенной
модели сервис работает на шаблонном тексте, и в ответе видно `"source": "template"`.

Используется Qwen3-4B-Instruct-2507 в кванте Q4_K_M (≈2.5 ГБ весов, ≈3.5 ГБ памяти при работе) —
помещается на MacBook Air M4 16 ГБ вместе с остальными сервисами.

```bash
mkdir -p models && cd models
curl -L -O https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF/resolve/main/Qwen3-4B-Instruct-2507-Q4_K_M.gguf
cd ..

llama-server -m models/Qwen3-4B-Instruct-2507-Q4_K_M.gguf --port 8080 --ctx-size 8192 --jinja
```

Форма `llama-server -hf unsloth/Qwen3-4B-Instruct-2507-GGUF:Q4_K_M` в сборке из Homebrew не
резолвится (`no remote preset found`), поэтому файл скачивается напрямую.

Другую модель можно подставить переменными окружения без правки кода:

```bash
export ML_LLM_BASE_URL=http://127.0.0.1:8080
export ML_LLM_MODEL=qwen3-4b-instruct-2507
```

## Как устроено

```
data.py       корпус CSV и база тренажёра (read-only) → единый SessionFacts
skills.py     SessionFacts → шесть навыков 0..100 → слабое место
recommend.py  слабое место → профильный сценарий (уровень, причина, ручки, шаги)
mining.py     все прохождения → системные проблемы → черновики новых сценариев
llm.py        текст для эксперта; при недоступности модели — шаблон
proposals.py  очередь предложений и решения эксперта (своя SQLite)
service.py    HTTP-ручки /ml/v1
cli.py        те же функции из терминала
config.py     все пороги, ручки и таблица «навык → методика тренировки»
```

Поток данных:

```
журнал прохождения
   → факты (data)
   → навыки и слабое место (skills)
   → профильный сценарий (recommend)
   → текст (llm)
   → черновик в очереди (proposals)
   → решение эксперта
   → внесение в тренажёр вручную
```

### Шесть навыков

| Навык | Что показывает |
|---|---|
| `safety` | Дисциплина команд: опасные действия, нарушения последовательности, повторы |
| `correction` | Выполнено ли действие, устраняющее причину, и как быстро |
| `diagnosis` | Названа ли первопричина верно |
| `detection` | Как быстро замечено отклонение после первой видимой тревоги |
| `verification` | Проверен ли результат и семь участков ниже по цепочке |
| `alarm_handling` | Подтверждение тревог на фоне второстепенного шума |

Навык может быть **не оценён** (`score: null`): проверять результат нечего, если корректирующего
действия не было. Не оценённый навык не может стать слабым местом — иначе рекомендация уводила бы от
настоящей проблемы.

Два правила сильнее арифметики:

- **любое опасное действие** делает безопасность слабым местом, даже если по штрафам балл выше порога;
- **неверный диагноз** снимает оценку с корректирующего действия: устранять было нечего, тренировать
  надо диагностику.

### Профильный сценарий

Рекомендация — это выбор значений ручек, которые тренажёр уже умеет (`backend/app/infrastructure/seed/scenario.py`):
уровень 1–3, первопричина (потеря производительности насоса или заедание регулятора), целевая ветвь,
задержка датчиков, темп второстепенных тревог, дедлайн реакции, скорость развития возмущения,
подсказки, задержка пуска резервного насоса. Ничего за пределами этого списка ML не предлагает —
за этим следит проверка `recommend._validate`.

Таблица «слабый навык → методика» лежит в `config.TRAINING_RECIPES`. Например, слабую диагностику
тренируют **другой** первопричиной: у неё другой наблюдаемый признак, и оператор учится различать
падение давления насоса и расхождение команды с фактическим положением регулятора.

### Границы

- База тренажёра открывается только на чтение (`file:...?mode=ro`).
- Скрытое состояние сценария не читается: список запрещённых полей в `config.FORBIDDEN_FIELDS`,
  проверка стоит на границе с базой в `data._assert_no_forbidden`.
- Первопричина прошлого прохождения не берётся из скрытой конфигурации, а выводится из журнала
  диагнозов оператора: причин ровно две, верный диагноз называет её прямо, неверный — исключает.
- Backend не изменён ни одним файлом.

## Что здесь изучать (junior ML)

Порядок, в котором стоит читать код, — он же порядок работы над любой ML-задачей:

1. **`data.py` — данные раньше моделей.** Два разных источника приводятся к одной структуре. Отдельно
   посмотрите, как отделены поля, которые нельзя подавать в модель (утечка будущего и скрытое
   состояние). Это первое, что проверяют в реальном проекте.
2. **`skills.py` — признаки и baseline.** Прозрачные правила дают объяснимый результат и служат точкой
   отсчёта. Любая будущая модель должна доказать, что она лучше вот этого baseline.
3. **`tests/test_skills.py` — валидация без обучения.** У каждого из шести профилей корпуса известен
   свой изъян. Если правила верны, слабое место совпадает с изъяном. Так проверяют методику, когда
   размеченных данных мало.
4. **`recommend.py` — от предсказания к действию.** Найти слабое место мало: система обязана
   предложить конкретное следующее упражнение и обосновать его числами.
5. **`mining.py` — от одного к группе.** Агрегат по всем прохождениям отвечает на другой вопрос, чем
   разбор одного человека, и требует порога «данных достаточно».
6. **`llm.py` — где уместна языковая модель.** Она пишет текст по посчитанным фактам и ничего не
   решает. Ответ приходит по JSON-схеме и всё равно проверяется, а отказ модели не ломает сервис.

Следующий шаг за пределами MVP: в корпусе размечен таргет `risk_next_30s` (28 116 снимков, 3 %
положительных). На нём обучается модель раннего предупреждения — и её качество сравнивается с
правилами из `skills.py` по PR-AUC с разбиением по `session_id`. Сейчас обучаемой модели нет
осознанно: сначала объяснимый baseline, потом обучение.

## Ограничения

- Пороги навыков и таблица методик — рабочее допущение уровня MVP, как и все значения в
  `seed/scenario.py`. Их подтверждает эксперт-методист, а не код.
- Корпус синтетический: 36 прохождений с шестью профилями поведения. Его хватает, чтобы калибровать
  пороги и проверять правила, но не чтобы обучать модель.
- Показ рекомендаций эксперту в интерфейсе и обратная запись утверждённых сценариев в тренажёр —
  отдельная задача. Сейчас утверждённое предложение отдаётся как JSON и вносится вручную.
