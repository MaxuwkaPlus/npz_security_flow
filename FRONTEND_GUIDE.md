# Гайд для фронтенда: API тренажёра ЭЛОУ-АВТ

Бэкенд — тренажёр оператора установки ЭЛОУ-АВТ. Сценарий: оператор пускает
установку, выводит её в устойчивый режим, затем бэкенд скрыто портит один
параметр (насос теряет производительность или клинит клапан), оператор должен
заметить это по приборам, поставить диагноз, устранить причину и проверить
последствия по всей цепочке. В конце — автоматический отчёт с оценкой.

Фронт — это пульт оператора: показания, кнопки команд и осмотров, тревоги,
форма диагноза, тесты SAGAT/NASA-TLX и экран отчёта.

Полный список ручек с примерами запрос/ответ — в [MANUAL_TESTING.md](MANUAL_TESTING.md)
и на `http://localhost:8000/docs`. Здесь — что для чего нужно и в каком порядке дёргать.

## Общие правила

- Base URL REST: `/api/v1`. WebSocket: `/ws/v1/sessions/{session_id}`.
- **Каждый запрос, кроме `/health`, `/ready` и `/auth/login`, требует токен**:
  заголовок `Authorization: Bearer <access_token>`. Без него — `401`
  с `code: MISSING_TOKEN`, с истёкшим или отозванным — `401 INVALID_TOKEN`.
  В обоих случаях сеанс закончился: чистите хранилище и показывайте экран входа.
- Права на действие проверяет сервер. `GET /auth/me` отдаёт список прав, по
  которому удобно прятать недоступные разделы, но это **удобство интерфейса**:
  спрятанная кнопка ничего не защищает, а отказ приходит `403 FORBIDDEN`
  с `details.required_any_of` — списком прав, любого из которых хватило бы.
- Ошибки — всегда один формат: `{"error":{"code","message","details","request_id"}}`.
  Разбирайте по `code`, `message` — просто для лога/дебага, не для показа
  пользователю as-is.
- Команда (`POST /actions`) в ответе имеет `status: "accepted"` или
  `"rejected"`, но никогда `"applied"` — принятая команда подействует на
  ближайшем шаге симуляции (обычно 1 секунда). Не считайте, что параметры
  изменились сразу после ответа.
- Правильность диагноза и классификация команды (`correct`/`dangerous`/...)
  **никогда** не приходят синхронно в ответ на действие оператора — это
  сознательное решение: тренажёр не должен подсказывать в моменте. Узнать
  результат можно только из итогового отчёта.
- `expected_version` в командах жизненного цикла — **необязательное** поле.
  Нужно, только если на одну сессию пишут два клиента (инструктор + оператор):
  берите свежий `version_no` из `GET /sessions/{id}/state` прямо перед
  отправкой. Не подставляйте константу — получите `SESSION_VERSION_MISMATCH`.
  Для одного клиента на сессию поле просто не отправляйте.

## `request_id` — обязателен, генерируйте сами

Ключ идемпотентности. Он защищает не столько установку, сколько **оценку
оператора**: дубликат команды классифицируется как `repeated` и снимает баллы
с безопасности. Без ключа сетевой retry испортил бы человеку результат.

**Правила:**

- **Обязателен** в теле почти каждого `POST` (исключения — в таблице ниже).
- **Формат:** строка 1–36 символов. Практически — UUID v4, генерируйте на
  клиенте.
- **Один запрос — один ключ.** Генерируйте в момент действия пользователя
  (нажал кнопку) и сохраняйте вместе с запросом в очереди отправки.
- **Retry — с тем же ключом.** Если ответ потерялся, повторяйте **тот же
  запрос целиком, с тем же `request_id`** — сервер вернёт прежний результат и
  не выполнит действие дважды.
- **Не переиспользуйте ключ для другого тела.** Тот же `request_id` с другим
  содержимым — это `409 REQUEST_ID_ALREADY_USED`. Сервер не станет молча
  подсовывать результат прошлой операции.

**Где нужен, а где нет:**

| Ручка | `request_id` | Идемпотентность |
|---|---|---|
| `POST /sessions` | обязателен | по ключу |
| `POST /sessions/{id}/start\|pause\|resume\|abort` | обязателен | по ключу |
| `POST /sessions/{id}/actions` | обязателен | по ключу |
| `POST /sessions/{id}/observations` | обязателен | по ключу |
| `POST /sessions/{id}/diagnoses` | обязателен | по ключу |
| `POST /sessions/{id}/alarms/{id}/acknowledge` | обязателен | по самой тревоге: повтор не меняет момент подтверждения |
| `POST /sessions/{id}/sagat/{id}/answers` | обязателен | по чекпоинту |
| `POST /sessions/{id}/actions/{id}/cancel` | **тела нет вообще** | по состоянию команды |
| `POST /sessions/{id}/nasa-tlx` | **нет такого поля** | одна анкета на сессию, повтор — `409` |

## REST vs WebSocket — кто за что отвечает

| | REST | WebSocket |
|---|---|---|
| Команды, наблюдения, диагноз, ответы SAGAT/TLX | ✅ | — |
| Разовые справочники (каталог, отчёт) | ✅ | — |
| Показания приборов (расходы, температуры, уровни) | ❌ нет такой ручки | ✅ единственный источник |
| Тревоги, статус команд, смена этапа — live-обновления | можно опросить `GET`, но неудобно | ✅ основной канал |

**Правило:** подключайтесь к WebSocket сразу после того, как сессия создана, и
держите соединение открытым весь сеанс. REST дёргаете только по действиям
пользователя (нажал кнопку) и для разовых справочников. Показания приборов на
экране обновляются **только** из WS-сообщений `process_snapshot` — polling'а
для них нет и не будет, это осознанное архитектурное решение.

## Экран за экраном

0. **Вход** — пульт открыт без входа. Если токена нет, клиент запрашивает
   `POST /auth/guest` и получает гостевую учётную запись с правами ровно на своё
   прохождение: `session.create`, `session.control_own`, `session.operate`,
   `session.read_own`, `report.read_own`. Инструктора у неё нет, поэтому ход
   прохождения она ведёт сама — но только своего.

   `POST /auth/login` с логином и паролем нужен там, где важно имя: инструктору,
   чтобы вести чужое обучение, эксперту — чтобы подписывать решения, обучаемому —
   чтобы прохождения остались за ним. В ответе `access_token`, `expires_at` и
   `user` с ролями и правами. Ответ на неверный логин и на неверный пароль
   одинаков: по нему нельзя перебрать существующие учётные записи.

   Дальше экран определяется правами: у кого есть `session.create` — заводит
   прохождение, у кого `session.control` — назначает его другому оператору,
   у кого `audit.read` — открывает журнал доступа. Рабочее место администратора
   ИБ вынесено на отдельный адрес `/admin`, и вход там обязателен.
1. **Выбор сценария** — `GET /scenarios`, `GET /scenarios/{id}` для списка
   уровней сложности. Показать уровни 1 (проще, есть подсказки) / 2 / 3
   (сложнее, без подсказок, больше помех-тревог). Нужен только тому, кто
   назначает обучение.
2. **Создание сессии** — `POST /sessions` (право `session.create`), затем сразу
   открыть WebSocket. `instructor_id` в теле не передаётся: сервер берёт его из
   токена, назначить сессию от чужого имени нельзя. `operator_id` чужим может быть
   только у того, кто ведёт чужое обучение (`session.control`); остальным сервер
   вернёт `403`. Именной обучаемый сессию не создаёт — он открывает назначенную
   из `GET /sessions`.
   Опционально `GET /installations/{id}/topology`, чтобы отрисовать P&ID-схему
   установки один раз при загрузке.
3. **Пульт оператора** (главный экран, работает до конца сессии):
   - панель показаний — из WS `process_snapshot`;
   - кнопки команд и осмотров — `POST /actions`, `POST /observations`;
   - лента тревог — из WS `alarm_raised`/`alarm_updated`, кнопка «квитировать»
     — `POST /alarms/{id}/acknowledge`;
   - кнопки управления сессией — старт/пауза/резюм/прервать.
4. **Форма диагноза** — открывается, когда оператор нажал «зафиксировать
   отклонение» (`observation_type: declare_deviation`) — `POST /diagnoses`.
5. **Модалка SAGAT** — открывается по сигналу из WS (см. таблицу типов ниже)
   или по опросу `GET /sagat/current` — `POST /sagat/{id}/answers`.
6. **Модалка NASA-TLX** — после `session_completed` — `POST /nasa-tlx`.
7. **Экран отчёта** — `GET /sessions/{id}/report`, для инструктора ещё
   `GET /operators/{id}/level-comparison`.

## Ручки по группам

Заголовки ниже совпадают с группами на `/docs` — там же у каждой ручки есть
короткое описание, что она делает.

### Доступ — вход и права

| Ручка | Зачем |
|---|---|
| `POST /auth/guest` | вход без учётной записи: токен на своё прохождение и ничего сверх него |
| `POST /auth/login` | вход по логину и паролю, в ответе токен и права |
| `POST /auth/logout` | отзыв текущего токена; другие сеансы не затрагивает |
| `GET /auth/me` | роли и полный список прав — по нему прячете недоступные разделы |
| `GET /roles` | матрица ролей и прав; `assignable: false` — роль следующего цикла |
| `GET /users`, `POST /users`, … | учётные записи и роли, право `account.manage` |
| `GET /security-events` | журнал доступа, право `audit.read` |

### Сервис и Каталог — экран выбора и справочники

| Ручка | Зачем |
|---|---|
| `GET /health`, `GET /ready` | индикатор «бэкенд жив» на экране загрузки |
| `GET /scenarios` | список доступных сценариев для выбора |
| `GET /scenarios/{id}` | уровни сложности (для селектора) и список этапов (`stages`) — по ним можно нарисовать прогресс-бар прохождения на пульте |
| `GET /installations/{id}/topology` | состав оборудования, связи и пороги тегов (`normal/warning/critical`) — рисуете схему установки один раз и знаете, при каком значении подсвечивать прибор жёлтым/красным |

### Сессия — управление прохождением

| Ручка | Зачем |
|---|---|
| `POST /sessions` | создать прохождение: оператор, сценарий, уровень сложности |
| `GET /sessions/{id}` / `/state` | получить текущее состояние — нужно как fallback при переподключении, когда WS оборвался и не восстановился сразу |
| `POST /sessions/{id}/start` | инструктор/оператор запускает симуляцию — с этого момента идёт время |
| `POST /sessions/{id}/pause` / `/resume` | пауза для разбора ситуации без давления времени — время симуляции реально останавливается |
| `POST /sessions/{id}/abort` | досрочно прервать — сессия сразу получает финальный итог «прервана», без оценки |

### Команды оператора — воздействие на установку

`POST /sessions/{id}/actions`. Это ручка, через которую отправляются **все**
управляющие кнопки на пульте: пуск насоса, открытие клапана, подача воды на
ЭЛОУ, включение перекачки на К-1, розжиг печей, переключение на резервный
насос, восстановление контура регулирования. Тип команды (`action_type`) и
адрес (`target_code`) определяют, какой ключ нужен в `value` и в каком
диапазоне.

Ответ — чек о приёме. В нём есть `value` — значение, каким его понял сервер:
удобно показывать в истории команд («клапан ветви 2 → 40 %») и проверять, что
уставка долетела правильно. Для беспараметрических команд там `{}`.

Отказ приходит **не как HTTP-ошибка**, а как `202` с `status: "rejected"` и
заполненным `rejection_reason`. Покажите его пользователю подсказкой, а не
красной плашкой «ошибка сервера»:

| `rejection_reason` | Что произошло |
|---|---|
| `unknown_action_type` | такого типа команды не существует |
| `target_not_allowed` | команда неприменима к этому оборудованию |
| `missing_value` | не передан обязательный ключ в `value` |
| `value_out_of_range` | значение вне допустимого диапазона |

Отклонённая команда всё равно попадает в журнал и в отчёт — попытка
недопустимого действия информативна сама по себе.

`POST /sessions/{id}/actions/{action_id}/cancel` — кнопка «отменить» рядом с
командой, которая ещё не применилась (в WS у неё `status: accepted`, не
`applied`). Тела у запроса нет. После применения отменить уже нельзя — кнопка
должна исчезнуть, как только по WS пришёл статус `applied`.

### Наблюдения и диагноз — явные действия осмотра

`POST /sessions/{id}/observations`. По сценарию оператор не может просто
«увидеть» состояние установки — он обязан явно проверить участок кнопкой
(например «осмотреть узел» на этапе пуска, или «сравнить расходы ветвей»,
«зафиксировать отклонение», «проверить последствия» после устранения причины).
Это не формальность: без обязательных осмотров этап не закроется (см.
`required_checks` из `GET /scenarios/{id}`), а именно `declare_deviation`
запускает отсчёт времени обнаружения, которое попадёт в отчёт. На пульте это,
скорее всего, набор кнопок «осмотреть X» рядом с каждым узлом схемы.

Форма диагноза — там же:

`POST /sessions/{id}/diagnoses`. Форма с тремя полями: какой участок
затронут, какое отклонение, какая предполагаемая причина. Открывайте её после
того, как оператор нажал «зафиксировать отклонение». Ответ не говорит,
правильно ли — это узнается только из отчёта.

### Тревоги

| Ручка | Зачем |
|---|---|
| `GET /sessions/{id}/alarms` | список активных тревог — дёргать при (пере)подключении, дальше жить по WS |
| `POST /sessions/{id}/alarms/{alarm_id}/acknowledge` | кнопка «квитировать» на карточке тревоги — неподтверждённые тревоги штрафуют итоговую оценку безопасности |

Тревоги 5 уровней (L1…L5, чем выше — тем серьёзнее) и уровень L0 —
второстепенные «шумовые» тревоги, не связанные с основной неисправностью,
показывайте их визуально слабее. Тревога гаснет сама, когда причина устранена
— кнопка квитирования не убирает тревогу с экрана, а только помечает как
подтверждённую.

### Оценка осведомлённости: SAGAT

`GET /sessions/{id}/sagat/current` — есть ли открытый чекпоинт прямо сейчас.
`POST /sessions/{id}/sagat/{checkpoint_id}/answers` — отправка ответов.

По сценарию симуляция в момент вопроса **не останавливается** (кроме случая,
когда вы сами вызовете `pause`) — это тест на то, успевает ли оператор держать
в голове картину происходящего. Вопросы приходят с вариантами ответов, без
подсказок и без верного ответа в теле — оценивается сервером.

### Оценка осведомлённости: NASA-TLX

`POST /sessions/{id}/nasa-tlx` — анкета из 6 шкал (0–10) после завершения
сессии, отправляется один раз. `request_id` у неё нет — идемпотентность по
самой сессии. На итоговую оценку прохождения не влияет: это отдельная метрика
для инструктора, не путайте с `resultiveness` в отчёте.

### Отчёты

| Ручка | Зачем |
|---|---|
| `GET /sessions/{id}/report` | финальный экран: итог (стабилизировано/нет), тайминги, 5 составляющих оценки, журнал команд и тревог, что из downstream-проверок пропущено, словесные выводы |
| `GET /operators/{id}/level-comparison` | для инструктора: как результативность оператора просела при переходе с лёгкого уровня на сложный |

## WebSocket

Подключение: `ws://.../ws/v1/sessions/{session_id}?token=<access_token>&last_sequence_no=0`.

`token` **обязателен** и идёт параметром запроса: браузерный `WebSocket` не умеет
задавать заголовки. Канал закрыт тем же правилом, что и чтение сессии по REST.
Отказ приходит кодом закрытия, а не сообщением: `4401` — нужен вход, `4403` — нет
прав на эту сессию, `4404` — сессии нет. На `4401` и `4403` **не переподключайтесь
циклически**: очистите сеанс или верните на список прохождений.

`last_sequence_no` — последний увиденный номер сообщения; при переподключении
передавайте сохранённое значение, а не `0` — сервер дошлёт пропущенное, ничего
не потеряется. **Храните этот номер в состоянии фронта**, обновляя после
каждого полученного сообщения.

Конверт одинаковый для всех сообщений:

```json
{ "schema_version": 1, "type": "...", "session_id": "...", "sequence_no": 42, "sim_time_ms": 183000, "payload": { ... } }
```

| `type` | Когда приходит | Что делать на фронте |
|---|---|---|
| `process_snapshot` | раз в 5 секунд симуляции | обновить панель показаний из `payload.values`/`payload.derived`; `payload.stage_code` — обновить прогресс этапа |
| `session_state` | старт/пауза/резюм/создание | обновить статус сессии (running/paused/...) |
| `session_completed` | сессия дошла до конца | заблокировать пульт, открыть модалку NASA-TLX, предложить перейти к отчёту |
| `stage_changed` | завершился очередной этап | обновить индикатор этапа, можно показать тост «этап X завершён» |
| `alarm_raised` | новая тревога | добавить карточку в ленту тревог |
| `alarm_updated` | тревога подтверждена или погасла | обновить состояние карточки |
| `action_status_changed` | команда принята/отклонена/применена | обновить статус команды в истории; когда пришло `applied` — убрать кнопку «отменить» |
| `session_event` | всё остальное (наблюдение записано, диагноз подан, команда отменена, действие классифицировано, SAGAT-чекпоинт открыт/отвечен) | смотреть `payload.event_type`; как минимум по `sagat_requested` — открывать модалку SAGAT вместо опроса `GET /sagat/current` |

В `payload` снимков и событий нет и не будет служебных полей вроде причины
возмущения, целевой ветви или внутренней «интенсивности» — это не баг, а
намеренное сокрытие: оператор должен догадаться по приборам, а не прочитать
ответ сервера.

## Коды ошибок, на которые стоит явно реагировать

| `code` | Когда | Что показать |
|---|---|---|
| `MISSING_TOKEN`, `INVALID_TOKEN` | нет токена, либо он истёк или отозван | очистить сеанс и показать экран входа |
| `INVALID_CREDENTIALS` | неверный логин или пароль | одно сообщение на оба случая — иначе можно перебирать логины |
| `FORBIDDEN` | у роли нет нужного права или ресурс чужой | не показывать действие заранее; `details.required_any_of` — чего не хватило |
| `ROLE_NOT_AVAILABLE` | выдаётся роль следующего цикла | брать роли из `GET /roles` с `assignable: true` |
| `WEAK_PASSWORD` | пароль короче 12 символов | подсветить поле пароля |
| `USERNAME_TAKEN` | логин занят | подсветить поле логина |
| `VALIDATION_ERROR` | не прошла базовая валидация тела/параметров | подсветить поле формы |
| `REQUEST_ID_ALREADY_USED` | тот же `request_id` с другим телом или в другой сессии | почти всегда баг генерации ключей на фронте — не ретраить, а чинить |
| `SESSION_NOT_RUNNING` | команда/наблюдение отправлены не на идущей сессии | заблокировать кнопки, пока сессия не `running` |
| `SESSION_TRANSITION_NOT_ALLOWED` | недопустимый переход (например `pause` до `start`) | не показывать кнопку в недоступном состоянии заранее |
| `SESSION_VERSION_MISMATCH` | устаревший `expected_version` | перечитать состояние (`GET /state`) и повторить |
| `ACTION_ALREADY_RESOLVED` | пытаетесь отменить уже применённую/отклонённую команду | убрать кнопку «отменить» |
| `OBSERVATION_TARGET_NOT_ALLOWED`, `UNKNOWN_OBSERVATION_TYPE` | неверный адрес/тип осмотра | обычно означает баг на фронте — сверить с каталогом кодов оборудования |
| `NASA_TLX_ALREADY_SUBMITTED` | повторная отправка анкеты | показать «анкета уже отправлена», не форму ошибки |
| `ALARM_NOT_FOUND`, `SAGAT_CHECKPOINT_NOT_FOUND` | квитируете/отвечаете по устаревшему id | перечитать `GET /alarms` или `GET /sagat/current` |
| `SCENARIO_NOT_FOUND`, `SESSION_NOT_FOUND`, `ACTION_NOT_FOUND` | битый/устаревший id | вернуть на экран выбора |

Остальные детали (точные пороги, тексты сообщений, полные примеры JSON) — в
