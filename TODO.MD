# Ревью приложения ЭЛОУ-АВТ

Дата: 2026-09-29. Область: frontend, backend, ML-сервис, документация, продуктовые сценарии.
Это backlog по результатам ревью, а не список реализованных исправлений.

**Приоритеты:** P0 — обход доступа/раскрытие результатов; P1 — нарушено прохождение или достоверность оценки; P2 — существенные UX-проблемы и технический долг; P3 — поддерживаемость.
**Доказательность:** «воспроизведено» — выполнена изолированная проверка; «код» — подтверждён путь в реализации; «риск» — необходим отдельный нагрузочный/браузерный тест. Визуальная оценка основана на JSX/CSS: интерактивное браузерное прохождение и пиксельное сравнение не выполнялись. Рабочая БД и пользовательские прохождения не изменялись.

## P0 — права доступа и утечки

- [ ] **SEC-01. Закрыть ML API серверной авторизацией и исключить подмену подписи эксперта.** **Воспроизведено.** `GET /ml/v1/proposals` без токена возвращает 200; `POST /ml/v1/proposals/{id}/approve` без токена принимает произвольный `expert_id` и записывает его в `reviewed_by`. Проверка выполнена через TestClient на временной SQLite с тестовым предложением. Аналогично не защищены сведения о сессиях и рекомендации, включая текущие прохождения. Скрытие кабинета во frontend этого не исправляет; `/ml` проксируется тем же Vite-сервером.
  Источники: [ML routes](ml/ml/service.py), [ML client](frontend/src/services/mlApi.js), [proxy](frontend/vite.config.js). Исправление: проверять principal и конкретные права на всех экспертных endpoints; подпись получать из аутентифицированной личности. Приёмка: anonymous → 401; trainee → 403; эксперт может утвердить только под своей подписью, решение попадает в аудит.

- [ ] **SEC-02. Убрать классификацию действий из операторского WebSocket.** **Код.** `action_classified` содержит `classification`, а `event_message` передаёт весь `payload_json` как `session_event`. Через сетевую вкладку оператор получает оценку correct/dangerous и другие классы до итогового отчёта, хотя DTO команды её скрывает.
  Источники: [classification](backend/app/application/classification.py), [realtime](backend/app/application/realtime.py), [guide](FRONTEND_GUIDE.md). Приёмка: белый список полей/типов операторского потока и контрактный тест на все классы событий, а не только снимки.

- [ ] **SEC-03. Запретить оператору получать оценку активной сессии через report API.** **Код.** Права на чтение своего отчёта проверяются, но терминальный статус не проверяется. `build_report` раскрывает классы действий и вывод о правильности диагноза во время прохождения. Скрытая кнопка отчёта не предотвращает прямой GET.
  Источники: [report routes](backend/app/api/v1/reports.py), [report builder](backend/app/application/reports.py). Приёмка: операторский отчёт доступен только после завершения; если инструктору нужен промежуточный отчёт, его контракт и права отделены.

## P1 — реальное время, прохождение и состояние клиента

- [ ] **RT-01. Согласовать события жизненного цикла с клиентом.** **Код.** Сервер отправляет `{from, to}`, клиент сливает payload в session и оставляет прежний `status`. Когда инструктор запускает/приостанавливает сессию в другой вкладке, оператор не получает правильное состояние кнопок. Локальный REST-ответ на действие маскирует проблему в одном клиенте.
  Источники: [session transitions](backend/app/application/sessions.py), [client receiver](frontend/src/hooks/useTrainingSession.js). Приёмка: две независимые вкладки синхронно показывают ready/running/paused/failed/aborted.

- [ ] **RT-02. Согласовать stage_changed и обновлять симуляционные часы.** **Код.** Сервер использует поле `to`; клиент ждёт `stage_code`/`to_stage_code`. Snapshot меняет только snapshot, но не `session.current_stage_code` и `session.sim_time_ms`. Заголовок этапа может меняться, тогда как номер этапа/прогресс и время остаются прежними до постороннего REST-обновления.
  Источники: [stages](backend/app/application/stages.py), [receiver](frontend/src/hooks/useTrainingSession.js), [progress](frontend/src/components/Header/StageProgress.jsx), [header](frontend/src/components/Header/AppHeader.jsx). Приёмка: каждый серверный снимок обновляет время и согласованную стадию без локальной симуляции часов.

- [ ] **RT-03. Передавать ID и статус команды в WS, обрабатывать отмену.** **Код.** Клиент читает `action_id/id` и `status`, но accepted/rejected/applied payload их не содержит; aggregate_id также не включён в envelope. Применение не обновляет REST-чек, появляются записи без ID/статуса, старый accepted остаётся отменяемым. `action_cancelled` приходит как session_event и игнорируется; REST-ответ отмены тоже отбрасывается. REST/WS могут дополнительно продублировать accepted.
  Источники: [actions](backend/app/application/actions.py), [tick](backend/app/application/tick.py), [projection](backend/app/application/realtime.py), [hook](frontend/src/hooks/useTrainingSession.js). Приёмка: одна строка на ID, полная цепочка accepted → applied/rejected/cancelled, отмена исчезает после разрешения.

- [ ] **RT-04. Сбрасывать WS cursor при смене сессии и восстанавливать очищенную проекцию.** **Код.** `sequence.current` живёт между sessionId; после сессии A с большим sequence сессия B открывается с этим же номером и пропускает историю. После «К списку» snapshot очищается, но повторное открытие той же завершённой сессии запрашивает только новые события: восстановить приборы нечем.
  Источники: [socket hook](frontend/src/hooks/useSessionSocket.js), [leave/open session](frontend/src/hooks/useTrainingSession.js). Приёмка: A → список → B и A → список → A восстанавливают состояние и последний снимок даже у завершённой сессии.

- [ ] **RT-05. Реализовать обнаружение пропусков и восстановление после переполнения WS-очереди.** **Код.** Hub теряет сообщения при QueueFull, рассчитывая на resync клиента. Клиент принимает любой больший sequence, не обнаруживает дыру и не проверяет session_id/schema_version; REST state не содержит приборов. После разрыва нет явного восстановления актуальных тревог/SAGAT/снимка.
  Источники: [hub](backend/app/infrastructure/realtime/hub.py), [socket hook](frontend/src/hooks/useSessionSocket.js), [session DTO](backend/app/api/v1/schemas/sessions.py). Приёмка: искусственный разрыв/медленный клиент не теряет команду, тревогу или checkpoint; cursor продвигается только после корректного применения сообщения.

- [ ] **RT-06. Прекращать уже открытый WS после отзыва доступа.** **Код.** Токен и права проверяются только перед подпиской. Logout, отключение пользователя, отзыв роли и истечение токена не закрывают существующий поток; это противоречит заявлению о немедленном отзыве.
  Источники: [WS handler](backend/app/api/v1/realtime.py), [auth](backend/app/application/auth.py), [spec §4](docs/BACKEND_PROJECT_SPEC.md). Приёмка: отзыв в другой сессии прекращает передачу без необходимости ручного reconnect. Отказ WS должен фиксироваться в security_events, а не только в logger.warning.

- [ ] **STATE-01. Изолировать состояние при смене пользователя/сессии.** **Код.** `useTrainingSession` не сбрасывается по user_id; leaveSession не очищает checkpoint, флаги диагноз/TLX, topology, notification. Открытие следующей сессии также не делает полного reset. Старые ответы запросов не проверяются по актуальному sessionId и могут перезаписать новую сессию; WS зависит от sessionId, но не от смены токена.
  Источники: [training hook](frontend/src/hooks/useTrainingSession.js), [App](frontend/src/App.jsx), [socket](frontend/src/hooks/useSessionSocket.js). Приёмка: смена identity и быстрые переходы не сохраняют чужие данные/модалки и не применяют запоздалые ответы. Использовать отмену запросов либо generation/session guard.

- [ ] **STATE-02. Обработать истечение гостевого токена.** **Код.** После успешного startGuest флаг guestRequested остаётся true. При 401 clearSession сбрасывает авторизацию; повторный startGuest немедленно возвращается, auth.error может оставаться null. Получается бесконечное «Готовим рабочее место…».
  Источники: [useAuth](frontend/src/hooks/useAuth.js), [TrainingWorkplace](frontend/src/App.jsx). Приёмка: истечение/отзыв гостевого токена переводит пользователя в явное восстанавливаемое состояние.

- [ ] **UI-01. Показать обязательные downstream-приборы и состояния оборудования.** **Код.** Metrics отбрасывает строки и делает `.slice(0, 18)`. При порядке visible_values остаются 15 параметров ветвей, давление насоса, вода и уровень первой ступени; К-1, печи, К-2, продукты и строковые статусы насосов скрыты. Оператор обязан подтверждать участки, показаний которых не видит.
  Источники: [Metrics](frontend/src/components/Dashboard/Metrics.jsx), [snapshot metrics](backend/app/domain/metrics.py). Приёмка: приборы всех обязательных участков доступны по понятным группам/вкладкам; состояния насосов отображаются явно, без ограничения по порядку ключей объекта.

- [ ] **UI-02. Заменить машинные коды в диагнозе понятными вариантами.** **Код.** По умолчанию отправляется причина `flow_control_fault`, тогда как сервер сравнивает её с `feed_pump_capacity_loss` или `flow_control_valve_stiction`. Оператору нужно знать внутренние строки; стандартный ответ никогда не признаётся правильным. Поля area/deviation сохраняются, но правильность зависит только от причины.
  Источники: [DiagnosisModal](frontend/src/components/Modals/DiagnosisModal.jsx), [diagnosis evaluation](backend/app/application/observations.py), [scenario](backend/app/infrastructure/seed/scenario.py). Приёмка: нейтральные, не раскрывающие ответ варианты из публичного каталога; без предвыбранной причины. Отдельно согласовать проверку всех трёх полей с методистом.

- [ ] **UI-03. Восстанавливать состояние NASA-TLX и дать выход из повторной анкеты.** **Код.** Replay session_completed всегда открывает TLX, даже если она уже отправлена. Повтор даёт 409, но модалка не закрывается и не имеет кнопки выхода. Также автоматическое открытие есть только для completed, не failed; политика послесессионной анкеты для всех исходов не определена в UI.
  Источники: [training hook](frontend/src/hooks/useTrainingSession.js), [TlxModal](frontend/src/components/Modals/TlxModal.jsx), [assessment](backend/app/application/assessment.py). Приёмка: повторное открытие завершённой сессии ведёт к отчёту либо к действительно незаполненной анкете; 409 корректно завершает этот UI-поток.

- [ ] **UI-04. Сделать отказ загрузки отчёта восстанавливаемым.** **Код.** useReport подавляет исключения, ReportPage остаётся в «Формирование отчёта…» без ошибки, retry и кнопки назад. Запросы отчёта и сравнения параллельны, хотя отчёт записывает SessionScore: первое сравнение может не включить только что рассчитанный результат.
  Источники: [useReport](frontend/src/hooks/useReport.js), [ReportPage](frontend/src/pages/ReportPage.jsx), [reports](backend/app/application/reports.py). Приёмка: offline/403/500 показываются явно; сравнение обновляется после готовности оценки.

## P1 — достоверность оценки и серверная надёжность

- [ ] **SCORE-01. Учитывать пропущенные/просроченные SAGAT-вопросы в знаменателе.** **Код.** `_sagat_totals` считает только сохранённые SagatAnswer. Просрочка меняет статус, но не создаёт нулевых ответов. Можно ответить правильно на одну точку, проигнорировать другую и получить оценку только по отвеченным вопросам. current_checkpoint не истекает автоматически и выбирает самый ранний open.
  Источники: [assessment](backend/app/application/assessment.py), [scoring](backend/app/application/scoring.py). Приёмка: максимум определяется реально назначенными вопросами, пропуск учитывается как согласованный нулевой результат; истёкшие точки не заслоняют следующие.

- [ ] **SCORE-02. Проверять downstream-наблюдения относительно времени корректирующего действия.** **Код.** ObservationFact не содержит времени, completed_checks собирает всю историю; ранний verify_result может закрыть будущую финальную проверку и добавить вес. `_unverified_actions` проверяет любое verify_result после действия без обязательной привязки к нужному участку.
  Источники: [observation domain](backend/app/domain/observations.py), [completed checks](backend/app/application/observations.py), [scoring](backend/app/application/scoring.py). Приёмка: клик «проверить продукты» до возмущения не подтверждает последствия последующей коррекции; правила времени/цели берутся из версии конфигурации.

- [ ] **SCORE-03. Исправить время обнаружения в отчёте.** **Код.** `_detection_time` использует выход из disturbance_monitoring вместо момента observation declare_deviation. Задержка/таймаут перехода этапа подменяет реакцию оператора. ML читает время наблюдения отдельно, отчёты могут расходиться.
  Источники: [report timing](backend/app/application/reports.py), [ML facts](ml/ml/data.py). Приёмка: эталонный журнал с разнесёнными observation и stage exit даёт время фактического обнаружения в обоих контурах.

- [ ] **SCORE-04. Убрать квалификационный балл у aborted и отделить промежуточные результаты.** **Код.** build_report вызывает calculate_scores для любого статуса; outcome_of проверяет параметры без требования completed (кроме aborted). Сравнение выбирает последний SessionScore уровня без фильтра завершённости/сценария. Прерванное либо промежуточное прохождение способно заместить завершённое.
  Источники: [reports](backend/app/application/reports.py), [outcome](backend/app/domain/report.py), [spec §8/17](docs/BACKEND_PROJECT_SPEC.md). Приёмка: aborted отображает отсутствие квалификационной оценки; сравниваются сопоставимые завершённые уровни с явной политикой выбора попытки.

- [ ] **SCORE-05. Связать штрафы с конкретными событиями.** **Код.** ScoreEventRecord создаётся без source_event_id, а все sim_time_ms равны времени пересчёта. Отчёт отдаёт aggregate reason/delta, но не позволяет перейти к конкретному событию-основанию.
  Источники: [scoring._store](backend/app/application/scoring.py), [model](backend/app/infrastructure/db/models/session.py), [report](backend/app/application/reports.py). Приёмка: у каждого штрафа есть правило, версия и одно или несколько событий-оснований с реальными моментами.

- [ ] **SIM-01. Реализовать заявленную задержку датчиков по уровню.** **Код.** sensor_delay_ms хранится, публикуется в каталоге и предлагается ML, но не используется в расчёте/выдаче снимков: поиск по backend/app находит лишь DTO, ORM, seed и публикацию. Обещанная часть сложности фактически отсутствует.
  Источники: [scenario](backend/app/infrastructure/seed/scenario.py), [tick](backend/app/application/tick.py), [realtime](backend/app/application/realtime.py). Приёмка: одинаковый процесс на уровнях выдаёт показания с настроенным запаздыванием выбранного датчика; семантика согласована со сценарием.

- [ ] **SIM-02. Восстанавливать running-сессии после рестарта и сообщать о падении tick.** **Код.** lifespan не запускает задачи для сохранённых running-сессий. При исключении `_tick_once` логирует сбой и возвращает None, задача завершается, статус остаётся running. Пульт показывает работающую сессию с замершими данными.
  Источники: [startup](backend/app/main.py), [runner](backend/app/infrastructure/runtime/session_runner.py). Приёмка: рестарт с файловой БД восстанавливает runtime без повторного применения команд; ошибка tick видна инструктору и имеет восстановительный сценарий.

- [ ] **DB-01. Сериализовать запись отчётов и убрать тяжёлый пересчёт из обычного GET.** **Код; конкурентный эффект — риск.** GET report удаляет и пересоздаёт SessionScore/SessionReport и score_events через обычный UoW вне runner.exclusive. Два читателя могут конкурировать друг с другом и tick; большой отчёт загружает всю историю снимков. Блокировки runner по sessionId не сериализуют всех писателей одной SQLite.
  Источники: [report endpoint](backend/app/api/v1/reports.py), [report store](backend/app/application/reports.py), [score store](backend/app/application/scoring.py), [runner](backend/app/infrastructure/runtime/session_runner.py). Приёмка: конкурентные report+report+tick не вызывают lost update/IntegrityError/database locked; финальный отчёт читается как версия готового результата.

- [ ] **ML-01. Сделать решение по предложению атомарным.** **Код; гонка требует конкурентной проверки.** proposals.review сначала SELECT-ит draft, затем UPDATE-ит по одному id без `status='draft'`. Два эксперта могут одновременно прочитать draft и перезаписать решение друг друга.
  Источник: [proposals.review](ml/ml/proposals.py). Приёмка: conditional UPDATE/CAS и проверка rowcount; из двух конкурентных решений только одно успешно, второе возвращает 409.

## P2 — UI/UX и продукт

- [ ] **UX-01. Исправить активные участки мнемосхемы.** **Код.** stageMarker возвращает пустую строку для нескольких узлов, а `stage.includes('')` всегда true. `includes('k')` также случайно совпадает с precheck.
