# Инструкции для агентов-разработчиков

## Назначение репозитория

Этот репозиторий предназначен для разработки backend-части MVP тренажёра операторов установки ЭЛОУ-АВТ. Тренажёр воспроизводит сквозной сценарий постепенного нарушения подачи сырья по одной из технологических ветвей, фиксирует действия оператора, рассчитывает состояние упрощённой модели установки и формирует объяснимый итоговый отчёт.

Перед любыми изменениями обязательно прочитай [полное техническое задание](docs/BACKEND_PROJECT_SPEC.md). Оно является главным проектным документом по бизнес-логике, архитектуре, данным, API и критериям приёмки.

Подробный предметный источник — [сценарий тренажёра](docs/TRAINER_SCENARIO.md). Если неясны этап, технологическая цепочка, состав оборудования, задача оператора, развитие возмущения, правильное или неправильное действие, тревога, критерий оценки либо содержание отчёта, сначала найди ответ в сценарии. Не заменяй отсутствующую информацию предположением. Если сценарий не отвечает на вопрос или противоречит техническому заданию, остановись, зафиксируй расхождение и запроси решение у команды.

## Приоритет источников

При противоречиях используй следующий порядок приоритета:

1. Текущая задача пользователя.
2. `docs/BACKEND_PROJECT_SPEC.md`.
3. `docs/TRAINER_SCENARIO.md` — для предметных подробностей, не определённых однозначно в спецификации.
4. Этот `AGENTS.md`.
5. `README.md` и остальные материалы репозитория.

`README.md` содержит раннюю версию концепции. Описание одиночного отказа насоса и обязательной ML-модели не является актуальным, если оно противоречит техническому заданию. Каталог `data/` — ранее подготовленный исследовательский материал, а не источник бизнес-правил backend.

## Текущие границы MVP

В текущую задачу входят:

- backend API и WebSocket-канал;
- управление жизненным циклом тренировочной сессии;
- конфигурация установки, сценария, уровней сложности и правил тревог;
- детерминированный упрощённый технологический двойник;
- регистрация действий оператора, событий, тревог и снимков параметров;
- детерминированная оценка действий;
- формирование итогового отчёта;
- миграции, тесты и техническая документация backend.

Без отдельного задания не реализуй:

- ML-модель, обучение, inference и feature pipeline;
- пользовательский интерфейс;
- реалистичный физико-химический симулятор НПЗ;
- интеграцию с реальной АСУ ТП, OPC, SCADA или производственным оборудованием;
- мобильное приложение, микросервисное разбиение, Kubernetes и облачную инфраструктуру;
- изменение или перегенерацию файлов в `data/`.

Для будущего ML допустимо предусмотреть интерфейс или порт, но текущая реализация должна работать без ML и не зависеть от него.

## Базовые технические решения

Если пользователь не изменил решение явно, используй:

- Python;
- FastAPI;
- Pydantic;
- SQLAlchemy ORM 2.x с declarative mapping и асинхронными сессиями;
- Alembic;
- SQLite через `sqlite+aiosqlite`;
- REST API с префиксом `/api/v1`;
- WebSocket с префиксом `/ws/v1`;
- модульный монолит.

Сначала проверь существующие `pyproject.toml`, lock-файл, команды и структуру проекта. Не создавай второй параллельный способ сборки или управления зависимостями.

## Архитектурные инварианты

- Backend — единственный авторитетный источник состояния сессии. Клиент отправляет намерения и отображает полученное состояние, но не рассчитывает технологический процесс, тревоги или баллы.
- Доменная логика не должна зависеть от FastAPI, SQLAlchemy, HTTP или конкретной базы данных.
- Время сценария — отдельное симуляционное время. Не смешивай его с системными часами.
- Для одной сессии должен существовать один последовательный поток изменения состояния. Не допускай параллельного применения двух тиков или двух конфликтующих команд.
- Повтор запуска с одинаковыми версиями конфигурации, `random_seed` и последовательностью действий должен давать одинаковый результат.
- Каждый принятый запрос на команду оператора должен иметь `request_id` и быть идемпотентным.
- Все события внутри сессии получают монотонный `sequence_no`; технологические моменты хранятся как `sim_time_ms`.
- Сценарий, схема установки и политика оценки версионируются. Завершённая сессия всегда ссылается на конкретные неизменяемые версии.
- Скрытое состояние сценария, будущие возмущения и эталонные действия никогда не передаются в операторский API или WebSocket.
- Пороговые значения, коэффициенты модели, временные окна и веса оценки должны находиться в версионируемой конфигурации, а не быть разбросаны по коду.
- Оценка должна быть детерминированной и объяснимой: каждый штраф и бонус связан с зафиксированным событием и правилом.
- `session_events` и действия оператора являются журналом аудита: их нельзя молча переписывать после фиксации.

## Правила предметной области и безопасности

Не придумывай самостоятельно реальные технологические нормативы, уставки защит, разрешённые действия или аварийные процедуры НПЗ. Значения из проектного документа считаются демонстрационными для MVP, пока эксперт команды не подтвердил иное.

Остановись и запроси решение, если задача требует:

- определить точную безопасную уставку или реальную противоаварийную процедуру;
- изменить причинно-следственную карту сценария или эталон действий оператора;
- отключить, обходить или имитировать обход блокировок безопасности;
- подключиться к реальному производственному контуру;
- собирать персональные данные сверх минимально необходимых идентификаторов участника.

## Работа с базой данных

- Основное хранилище MVP — файловая SQLite. Не добавляй PostgreSQL, отдельный сервер БД или второй persistence-стек без прямого задания пользователя.
- Доступ к данным реализуй через SQLAlchemy ORM 2.x: `DeclarativeBase`, `Mapped`, `mapped_column`, mapper-ы, репозитории и unit of work.
- ORM-модели относятся к инфраструктуре. Не возвращай их непосредственно из API и не размещай в них бизнес-правила.
- Все изменения схемы оформляй миграциями Alembic.
- Не редактируй уже применённую миграцию; создавай новую.
- Не выполняй разрушающие миграции и массовое удаление данных без явного согласования.
- Для изменений таблиц, не поддержанных SQLite напрямую, используй Alembic batch operations.
- Используй UUID на уровне домена/API с хранением канонической строкой, UTC для реального времени и целое число миллисекунд для симуляционного времени.
- На каждом рабочем соединении включай `PRAGMA foreign_keys=ON`; настрой `journal_mode=WAL` и ограниченный `busy_timeout`.
- Используй файловую SQLite для integration, migration и recovery-тестов. In-memory БД не подтверждает эти сценарии.
- Делай транзакции короткими и сериализуй запись внутри одного экземпляра приложения. Не скрывай `database is locked` бесконечными retry.
- Файл БД, `-wal` и `-shm` должен быть исключён из Git.
- Для денежных типов здесь нет оснований; для технологических значений выбирай числовой тип осознанно и одинаково во всех слоях.
- Соблюдай внешние ключи, ограничения уникальности и перечисленные в ТЗ инварианты.
- Большие снимки процесса не дублируй без необходимости. Частота записи должна настраиваться.
- Не сохраняй пароль, токен или секрет в коде, миграции, фикстуре, логе либо примере конфигурации.

## API и события реального времени

- Контракты должны быть типизированы и отражены в OpenAPI.
- Для ошибок используй единый стабильный формат с машинным `code`, понятным `message`, `details` и `request_id`.
- В изменяющих состояние запросах проверяй допустимость перехода и ожидаемую версию сессии.
- WebSocket-сообщения должны содержать `schema_version`, `session_id`, `sequence_no` и `sim_time_ms`.
- Повторное подключение клиента должно позволять получить актуальный снимок и продолжить с последнего известного номера события.
- Не включай в публичные ответы внутренние исключения, SQL, секреты или скрытые поля сценария.
- Изменил контракт — обнови схему, примеры и контрактные тесты в той же задаче.

## Стиль реализации

- Используй аннотации типов для публичного и доменного кода.
- Разделяй HTTP-слой, прикладные сценарии использования, домен и инфраструктуру.
- Не размещай бизнес-логику в роутерах и ORM-моделях.
- Не выполняй блокирующие операции внутри асинхронного обработчика.
- Зависимости передавай явно; глобальное изменяемое состояние не используй.
- Избегай больших универсальных сервисов и файлов. Модуль должен иметь одну ясную ответственность.
- Не подавляй исключения без регистрации и осмысленного преобразования.
- Логи делай структурированными и связывай через `request_id`, `session_id` и при наличии `operator_id`.
- Не добавляй производственную зависимость, если задачу можно решить текущими средствами; необходимость новой зависимости объясни в итоговом сообщении.
- Комментарии должны объяснять причину или ограничение, а не пересказывать код.

## Порядок работы агента

Каждое задание и каждая функция выполняются поэтапно. До правок разбей работу на малые последовательные подзадачи с одним наблюдаемым результатом и одной проверкой на шаг. Одновременно может выполняться только одна подзадача. Не переходи к следующей, пока текущая не реализована, не проверена и не отмечена завершённой.

До изменения кода:

1. Проверь состояние репозитория и не затрагивай посторонние изменения пользователя.
2. Прочитай относящиеся к задаче разделы технического задания.
3. Если задача затрагивает предметное поведение тренажёра, сверься с `docs/TRAINER_SCENARIO.md`.
4. Найди существующий путь выполнения функции от API до данных и тестов.
5. Сформулируй конкретный критерий готовности функции и её негативные случаи.
6. Разбей функцию на малые шаги и зафиксируй порядок выполнения; держи только один шаг в статусе `in_progress`.
7. Зафиксируй допущения, если спецификация и сценарий оставляют несущественный выбор.
8. Выбери минимальный вертикальный срез, который можно полностью проверить.

Во время реализации:

- выполняй шаги строго последовательно: контракт поведения → доменное правило → хранение/миграция → use case → API/WebSocket → тесты → документация;
- если слой не нужен, явно отметь его как неприменимый, а не создавай заглушку;
- после каждого шага запускай минимальную целевую проверку; при ошибке исправь текущий шаг до продолжения;
- не объединяй в одном шаге несколько независимых функций или несвязанный рефакторинг;
- меняй только файлы, необходимые текущей задаче;
- не проводи массовый рефакторинг одновременно с функциональным изменением;
- сначала реализуй доменное правило, затем прикладной сценарий, адаптеры и API;
- добавляй миграцию и тесты вместе с изменением модели данных;
- сохраняй обратную совместимость контракта, если её отмена не согласована.

После реализации:

- запусти относящиеся к изменению тесты, затем полный доступный набор проверок;
- проверь миграцию вперёд на чистой базе и, если безопасно поддерживается, откат;
- проверь OpenAPI и WebSocket-контракты;
- кратко перечисли изменённые файлы, выполненные проверки, допущения и оставшиеся ограничения.

## Тестирование

Каждое новое правило должно иметь тест на нормальный путь и на критичные границы. Для backend MVP нужны:

- unit-тесты переходов состояний, технологического расчёта, тревог и scoring;
- тесты прикладных сценариев с подменёнными портами;
- интеграционные тесты SQLAlchemy ORM-репозиториев и Alembic-миграций на временной файловой SQLite;
- тесты внешних ключей, WAL-настроек и конфликта конкурентной записи SQLite;
- контрактные тесты REST и WebSocket;
- сквозной тест полного сценария от запуска до отчёта;
- тест воспроизводимости по `random_seed` и журналу действий;
- тесты идемпотентности команд и защиты от гонок.

Используй команды, определённые самим репозиторием. Если проект создан на `uv` и иных команд пока нет, ожидаемый минимальный набор выглядит так:

```bash
uv sync
uv run alembic upgrade head
uv run ruff check .
uv run ruff format --check .
uv run mypy backend/app
uv run pytest
```

Не утверждай, что проверка прошла, если она не запускалась или завершилась ошибкой.

## Критерии завершения задачи

Задача backend завершена, когда одновременно выполнено следующее:

- поведение соответствует техническому заданию и критериям приёмки задачи;
- нарушенные ранее сценарии не появились;
- тесты добавлены и проходят;
- схема данных сопровождается миграцией;
- API и события документированы;
- ошибки обрабатываются единообразно;
- отсутствуют секреты, случайные персональные данные и утечка скрытого состояния;
- итоговый ответ содержит результат, проверки, допущения и известные ограничения.
